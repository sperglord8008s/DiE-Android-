# MPV media and codec investigation

Open **File info → MPV / media codecs / containers / stream metadata**. This invokes actual libmpv through the private isolated worker. The Android engine comes from the hash-pinned official mpv-android 2026-09-17 release (`mpv v0.41.0-1049-g0b7ed670f`). Engine/source identities, input SHA-256, guarded options, worker identity, budgets and read/seek counts accompany exports. See [source/build/license details](../media-engine/README.md).

## Read the evidence

The default table contains attempted file/stream/chapter properties with their exact availability/error state. Open an available property's **typed value / children** to investigate every map/array member. Track records expose the library's actual container/demuxer stream facts: codec/decoder names and descriptions, language/title/disposition flags, channel/rate/bitrate information, dimensions and other fields returned by that exact engine. Missing fields are not filled with guesses. Chapter/edition and tag trees preserve returned relationships and values.

Each property includes its source-pinned upstream manual block, including mechanisms, units, subproperties and limitations. For example, `duration` is an estimated number of seconds; decoded `audio-params` differ from the container's track declarations; `video-params` can contain decoder/override values; tracks can be limited to the current edition. These are observations made by libmpv. They do not establish authenticity, malware behavior, decoder safety, the integrity of every packet/frame or successful playback on a particular Android device.

**Root views** also expose every attempted file/engine property, unavailable properties, engine versions/codec/demuxer/protocol capabilities, all runtime property names, captured pre-load diagnostics, fixed initialization options and complete source/process/coverage provenance. Catalog names and decoder support describe the engine; they do not prove a selected file uses a codec or that Android hardware can decode it. The full property-name catalog is retained without invoking unrelated audio-device, clipboard or system-state getters. The audited capture set currently contains 53 file/engine getters; version-dependent missing properties retain their exact API error rather than disappearing.

## Exact values and navigation

- MPV maps retain an ordered array of keyed entries, including duplicate keys. Arrays keep their original order. Each child links to its complete typed descendants; the common viewer retains Back/filter/page state and recreation.
- Signed 64-bit values retain exact decimal identity. Doubles retain IEEE-754 bits, including signed zero/nonfinite distinctions. Strings and map keys retain the exact bytes supplied by the engine as UTF-8 hex, alongside the decoded display value; invalid UTF-8 display replacements are distinct from those bytes. The upstream C-string API cannot reveal content beyond an embedded NUL. Returned values are distinct from the original stored file representation.
- Interactive values/keys and hex are explicit previews. Search matches current keys/value previews. Complete table and selected-record JSON exports stream full native property/node data, independent of current filter/page. String leaves additionally export full text or exact engine-supplied UTF-8 bytes; byte-array leaves export every value byte. Exports are staged before the document picker and can finish after source expiry/recreation.
- MPV does not expose general physical offsets for decoded tags/tracks/chapters. These rows retain null locations. The source summary can open the actual private input in hex; no decoded-value offset becomes a file carving range.

The source-built metadata-extractor/XMP tool provides additional EXIF/IPTC/ICC/image-specific observations. Whole-blob Binwalk scanning discovers embedded signatures and parser-bounded stored-byte ranges. These tools remain complementary: a reported MPV metadata value is not itself an embedded-file extraction, and a Binwalk match is not a full media decode.

## Acquisition and process limits

The input is copied/hash-identified into an owned private snapshot before probing. Production transfers only read-only input and report descriptors plus a fixed engine enum to a nonexported isolated-UID service; there is no ordinary-UID fallback. Native callbacks serve only the fixed `dieblob://selected` input using `pread`, preserving caller descriptor position/ownership. Configuration, scripts, automatic profiles, automatic sidecars, referenced files and hardware decoding are disabled. A fixed libavformat demuxer, restricted protocol option and absence of INTERNET permission further constrain acquisition. Audio/video output is null and initialization is paused; software initialization can decode initial packets to discover stream parameters.

Budgets are 256 MiB input snapshot, 32 MiB cumulative input reads (including rereads), 25 seconds for native probing/property capture/teardown, 45 seconds at the parent request boundary, 4,096 catalog names, 100,000 nodes/depth 64, 8 MiB per string/byte value, 32 MiB native output and 1,000/256 KiB pre-load diagnostic events. Native output limits fail explicitly without successful partial reports. Unsupported/unprobeable inputs retain an **UNSUPPORTED / INCOMPLETE** banner, load error and available engine diagnostics/capabilities. A worker crash, incomplete pipe, timeout or failed guard returns an explicit error. The diagnostic list captures warnings/errors consumed before file-loaded/end; it is not a complete ongoing playback log.

Cancellation targets the request token and unbinds the isolated worker. Native callbacks observe their deadline/cancellation and an external process boundary can handle a parser that does not return. This design is wired, but actual isolated UID/Binder transfer/process death/cancellation timing is not yet verified on Android hardware. Other existing engines have not been migrated to this worker. Process isolation and byte/time budgets do not establish that every media parser accepts hostile data safely.

## Implemented versus verified

The ARM64 probe compiles against pinned upstream API headers; the nine official runtime libraries are copied without modification and checked again inside the APK. Signing, application identity, offline permissions, full notices/reference assets and static 16 KiB alignment of all twelve native libraries pass locally. Complete MPV dependency/submodule source archives, licenses and source-layout preparation are verified; a separate component-source ZIP is published by CI. The full upstream NDK r30 engine source build has not been run here; the tested APK build uses the pinned official runtime.

Host `scripts/test-mpv.sh` uses a real installed libmpv (the observed local runtime is 0.40.0, separate from the Android pin). Generated WAV/Matroska fixtures verify actual PCM/FFV1/SubRip recognition, three streams, Unicode/large tags, chapter metadata, catalogs, typed/exact exports, descriptor ownership, private snapshot lifetime, unsupported inputs, limits and rejection of a reference-bearing HLS playlist without accessing a test HTTP endpoint. This is a bounded fixture set, not exhaustive media coverage or full playback verification.

Four additional API 28 Robolectric checks use actual host MPV JNI with only OS worker transport substituted. They validate typed track/reference/search navigation, staged metadata bytes through picker delay/input expiry/recreation, decoder paging/recreation/full exports and explicit unsupported/unavailable states with cleanup. The Android suite now has **43 checks**. These do not verify production Binder/UID behavior, ARM64 codec execution, a real document provider, handset layout, API 26/35 runtime or actual 16 KiB device execution.
