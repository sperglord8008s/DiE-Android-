# Collected file metadata

Open **File info → Collected metadata / EXIF / IPTC / ICC / XMP** for the selected file. The tool lists every directory/tag returned by the integrated readers, then exposes directory relationships, engine diagnostics, XMP schema/property/array/qualifier nodes and complete values through Root views and record actions. An owned private snapshot and newly measured SHA-256 identify the bytes. No inspected application is loaded or executed, and XML references are not fetched.

## Engines, source and licensing

The `metadata-engine` module compiles **metadata-extractor 2.22.0** from its SHA-256-pinned source JAR (Apache-2.0; upstream tag commit `0aaf9d6f9d55704a79b1b1824f0efa97051f11d2`) with **Adobe XMP Core 5.1.0-jc003** from BSD-licensed AOSP commit `c60127d527f8438b89f9e292200639ec14d1c3cf`. `scripts/fetch-metadata.sh` verifies both source archives, prepares only library code and applies the complete checked-in `patches/metadata-engine.patch`. `METADATA_DEPS_DIR` supports a cached offline acquisition. No Maven XMP binary or source from a mirror with conflicting licensing notices is shipped. Full Apache/BSD terms and retained source-header notices are bundled and checked in APK verification.

The patch changes XMP namespace imports, adapts two old iterator return types, removes the newer reader's silent 1,000-item Photoshop ancestry restriction and inserts the app's bounded XML gate. It also retains the gate's diagnostic reason. The app fails explicitly at model budgets instead of silently dropping ancestry items. This source-built combination is not advertised as Adobe XMP 6.1.11 or equivalent feature coverage. See [module build notes](../metadata-engine/README.md).

## Scope and interpretation

The upstream dispatch includes JPEG, TIFF/DNG and several camera RAW families, PNG, BMP, GIF, ICO, PCX, Photoshop PSD, WebP, AVI, WAV, MP3, QuickTime/MP4, HEIF/AVIF, EPS and related formats. Current generated fixtures verify JPEG/EXIF/GPS/ICC/XMP, PNG text and WAV audio/INFO data; other dispatched readers are integrated but unverified here. Identification-only formats, including PDF/ZIP, have an explicit `identification-only` status/diagnostic. Unknown/invalid inputs retain an unsupported diagnostic and source identity. Reader warnings/errors stay visible and mark partial scope; an empty tag list is not a clean-file verdict.

Tag identifiers are scoped by directory instance/class. Repeated directory instances and parent links are retained. The upstream engine may already overwrite a repeated tag ID within one directory; the adapter cannot recover fields the engine did not return. Descriptions are engine interpretations, kept separate from raw typed values. EXIF timestamps can lack time zones, GPS data can be sensitive, and camera/software/author names are editable claims, not authenticated identity or provenance. No file-system attributes from the temporary copy are mislabeled as original SAF attributes.

Raw values preserve type names, integer/long decimal strings, exact rational numerator/denominator, float/double strings and IEEE bits, dates as engine epoch milliseconds/UTC interpretation, string charset/original bytes when supplied, arrays/collections and trusted engine value-model fields. Unknown non-engine value classes explicitly disclose string-only representation. These are returned engine values, not a claim to preserve every original serialization detail. No class from an inspected app is reflected or executed.

General tag offsets are unavailable from this API, so their physical locations remain null. Binary value chunk offsets and text-unit offsets index the **returned value**, not the source file. Source summary/hex actions use the owned original bytes. Do not treat a copied ICC value, normalized XMP path or associated description as a validated source range.

## XMP and XML

The viewer enumerates schemas, compound nodes, array elements and qualifiers, rather than flattening them into a map. Namespace, original iterator path, node kind, language where supplied and raw option bits remain visible. This older iterator spells qualifier paths such as `dc:title[1]/xml:lang`; `nodeKind: qualifier` makes their role explicit. Paths are engine output, not byte offsets or a promise of interchangeable lookup syntax. Upstream XMP normalization/encoding repair remains distinct from the original packet bytes.

Before the upstream DOM parser runs, `XmlGate` captures bounded content and validates it with SAX. All DTD declarations, external entities and URI-only input sources are rejected. Required lexical callbacks must be available or parsing fails explicitly. Limits per XML packet: 8 MiB bytes or four Mi UTF-16 units, depth 64, 100,000 elements and 10,000 attributes on an element; text/attribute values share the four-Mi-unit budget. Namespace URI attributes are ordinary data, not network requests. Cancellation is checked during capture and SAX events. Tests reject UTF-8/UTF-16 external-entity declarations and excessive depth.

## Large values, search and exports

Interactive tag values have bounded previews: up to 4,096 text units, 128 binary bytes and 16 array elements, with additional depth/node limits. Engine description previews cap at 16,384 units. Completeness markers are explicit. Complete value views expose binary data in 64 KiB chunks, strings in 4,096-unit chunks and array elements as records; JSON preserves isolated UTF-16 units if a boundary splits a pair. Binary values have exact byte export, and decoded text/XMP property values have complete text export. Text export fails on invalid unescaped UTF-16 rather than substituting characters; JSON exports escape those exact units.

`org.diemobile.evidence-table` exports every row in the selected scope regardless of the display filter/page. Metadata tag/value rows stream **`fullRawValue`**, and tag rows stream **`fullEngineDescription`**. XMP rows stream **`fullPropertyValue`**. Interactive preview fields remain alongside these complete fields. Selected-record export uses the same full-value writer. Full binary Base64 output is streamed; large values do not need a second full JSON DOM. Reports/binary bytes are privately staged before the document picker, so input expiry or recreation cannot alter a pending export. The shared search checks decoded names/fields as well as JSON serialization, including escaped slashes; preview-scoped fields still require complete-value views for their remaining content.

Limits: 128 MiB input; 20,000 directories; 200,000 tags; 10,000 diagnostics; 100,000 indexed XMP nodes/eight Mi indexed UTF-16 units. Complete value serialization caps one million nodes/32 levels, and value views one million parts. The shared 256 MiB encoded export budget still applies. Exceeding a budget fails explicitly without a successful partial export. Reader allocation/decompression can occur before adapter checks; parsing remains in process. Hard memory/CPU/process isolation, abandoned-cache reclamation, broader format fixtures and real-device verification remain pending.

## Verification

Run `bash scripts/test-metadata.sh` with JDK 17 and Python 3. It fetches/checksums source snapshots, applies the patch, compiles both real readers and tests generated data. `JSON_JAR` / `METADATA_DEPS_DIR` permit cached, checksum-verified offline reruns. Fixtures cover a valid generated JPEG with EXIF/GPS, repeated comments, split ICC data containing a false JPEG-end marker, 1,005 ancestry items, XMP arrays/language qualifiers/large properties, repeated PNG text and WAV PCM/INFO. Assertions check raw rationals/numeric bits, complete streamed record/table/binary exports, all chunk bytes, private ownership, cancellation, unsupported versus identification-only status and XML DTD/entity/depth boundaries. The small base JPEG was generated with FFmpeg; no third-party photo is redistributed.

Six API 28 Robolectric metadata cases exercise raw facts/parent links, XMP paging/search/Back/recreation, complete selected-record and exact binary export after source mutation/expiry, DTD diagnostics and cancellation/cleanup. They join the prior 31 cases for **37 Android checks**. Real SAF grants/providers, handset XML implementations, API 26/35 lifecycle, large-file performance and ARM64/16 KiB runtime remain unverified. This is collected metadata coverage, not every possible metadata field in every selected file, and does not implement MPV or Binwalk.
